# Loom: direction (2026-11-06)

Chris asked for three things. This doc covers each, then lists the decisions still open.
1. Name options.
2. A cleaner look, based on three references: WireViz, RapidHarness, and Wirely. The doc also
   audits existing harness software for ideas.
3. Integration with PL and EE.


## 1. Names

"Loom" also clashes with Loom, the well-known screen-recording product, which matters for search
and for talking about it. The suite's checkers are *-check* (Fabcheck, Partcheck), and its
reviews are *Signoff X*. This tool designs harnesses, so it can have a name of its own.

| Name | Why it fits | Against |
| --- | --- | --- |
| **Loom** (keep) | Wire loom is the trade's word for a bundle. Short, and already in the code (`LM`, `loom.v1.*`). | Clashes with Loom the video product |
| **Lacing** | Lacing cord ties harness bundles. A craft word, like Dovetail. | Less obvious to non-harness people |
| **Formboard** | What the shop builds on | Names one view, not the tool |
| **Pinout** | Says what you do in it | Generic, and many pinout sites use it |
| **Strand** | Short and quiet | A strand is part of a wire, not a harness |
| **Tieline** | Tying things together, between boards | Means something else in telecom |
| **Signoff WH** | Puts it in the Signoff family next to EE, ME, and FW | It isn't a review tool |
| **Wirecheck** | Matches Fabcheck and Partcheck, and it does run checks | It mainly draws, not checks |

Recommendation: **Loom** if it stays its own tool, **Lacing** if the clash bothers you. Renaming
later is cheap while it has no repo (folder, `<title>`, sidebar, and storage keys).

## 2. The look: from a formboard editor to a connection diagram

### What the references have in common

- **Image 1 (WireViz)** and **image 3 ("Generated by Wirely", a WireViz-style generator)** are
  *connection diagrams*:
  - Connectors are tables: a header (`X1`), a row of type, gender, and pin count, then one row per
    pin with label and number. Wirely shows unused pins as empty rows.
  - Each cable or bundle is a box in the middle: a header (`W1`), a row (`4x | 0.14 mm² (26 AWG) |
    0.2 m`), then one row per wire, `X1:1  BK  X2:1`.
  - Wires are smooth curves drawn in the wire's color with a thin dark outline, and they pass
    *through* the cable box.
  - Free ends are simple boxes: "Crimp ferrule, 0.25 mm²".
  - The sheet is white, with black hairlines, no shadows, and no handles.
- **Image 2 (RapidHarness)** is a *system* diagram. It shows devices with their connector stubs
  and harnesses between them (`Harness1 [6]`). It also has numbered note balloons, a revision
  table and a title block. That view belongs in PL, not in the harness editor (see section 3).

### What changes in Loom

The data model stays. The segment graph in `model.js` already holds everything images 1 and 3
show:

| On the reference | In Loom's model now |
| --- | --- |
| Connector table rows | `pinList(n)`. **Add `n.pinLabels`.** Labels now live on wires (`w.signal`), but WireViz puts them on pins, and so will EE nets. |
| Cable box rows `X1:1 BK X2:1` | `fromTo()` rows |
| Cable header `4x · 26 AWG · 0.2 m` | `group` (kind `cable`) plus `wireLen` |
| Twisted pair or shield marks | `group` kinds `twist` and `shield` |
| Ferrule or flying-lead box | families `ferrule` and `ring` |
| BOM | `bom()` |

What gets replaced is the **canvas** (`render.js`, most of `app.js`):

- **Connection view** becomes the default editor. It has a white, paper-like canvas with
  WireViz-style tables, cable boxes, and outlined curves.
  - Ends go on the left and right, and cable or bundle boxes go in the middle.
  - Layout is automatic, so there's nothing to drag except to reorder.
- **No + bubbles or handles.**
  - Add a connector or a cable from the side pane.
  - Wire by clicking a pin row, then a pin row on another end. That's the current gesture, on
    table rows instead of dots.
  - Edit a wire in the wire table or the inspector.
  - Shift-click selects several wires, and **Group** makes them a cable, twisted pair, or shield.
- **Formboard** (topology, segment lengths, breakouts, coverings) moves to a secondary *Layout*
  view, editable later. For now a wire's length is entered on its cable box, and each end pair
  gets a direct segment behind the scenes. That's compatible with the stored model.
- **Drawing** keeps one sheet: the connection diagram, connector faces, wire list, BOM, notes, a
  revision table and a title block. It takes Wirely's zone grid and RapidHarness's numbered note
  balloons.
- **Style:** the app chrome moves to **EE's current `styles.css`**, which is the most polished
  (Chris). Loom's `assets/suite.css` is a stale copy from 2026-11-02 (38.7 KB against EE's
  48.5 KB). Sync it from EE with a `tools/sync_suite_css.py` like the hub's, and add Loom to the
  engine-copy table in the root CLAUDE.md. The diagram itself uses the paper look, in both
  themes.

**Open question: how cable boxes group wires** on a branched harness. The demo has breakouts and
splice S1. Pick one:
- (a) one box per end pair;
- (b) **a box per cable group, with loose wires bundled per end pair** (recommended; it matches
  WireViz's cable and bundle);
- (c) a box per shared segment span.

With (b), splices draw as a small node between two boxes, as WireViz does.

### First cut (stripped back)

1. Connectors as tables, with pin labels and `mpn`, `gender`, and `pins`.
2. Wires, with color, gauge, and signal.
3. Cables and bundles, with twist and shield marks.
4. The wire table and BOM.
5. The sheet, with notes, revision table, title block, and print.

Everything else waits in the options list below until it's needed.

## 3. Integration: EE fab files → PL → Loom

### What exists

- Fabcheck already parses the **IPC-356 netlist**: one record per pad, with refdes, pin, and net
  (`pcb_dfm/assets/ipc356.js`). It also parses the **BOM**, with designator, MPN and
  manufacturer (`assembly.js`).
- Both files survive. They're inside the `package.zip` that Send stores at
  `fabcheck/<projectId>/runs/<runId>.json` in the project's private repo, and EE's Revisions tab
  tags these runs.
- PL reads only `meta` and `summary` from a review, and the summary is derived only from the
  document and the checklists. So connectors have to reach the **EE document** before they can
  reach the summary.

### Proposed path

1. **Fabcheck: find connectors.** At analysis time it builds `run.connectors`, a small list in the
   run record. Each entry is `{ ref, mpn, mfr, desc, pins: [{ pin, net }] }`.
   - A part counts as a connector if its refdes prefix is `J`, `P`, `CN`, `X`, or `CON`, or its BOM
     description matches *connector* or *header*.
   - Pins and nets come from the netlist.
2. **EE: carry them into the document.** Tagging a revision copies `connectors` from the run into
   the `revisions` record. `withSummary` then adds `summary.connectors` from the latest tagged
   revision. That keeps the summary contract: derived, never merged, and readers cope when it's
   missing.
3. **PL: a board shows its connectors.** A board Part's inspector gets a **Connectors &
   harnesses** subsection. It lists each board connector with the harness Parts plugged into it.
   - **Define harness** on a connector creates a harness Part (a new kind), with ends recorded as
     `{ part, ref }`.
   - It then opens Loom in the same tab (suite rule) at `loom/?pl=<harness id>`.
   - PL's Map could later draw the RapidHarness-style system view: boards as blocks with
     connector stubs and harness lines with wire counts.
4. **Loom: start from what the board knows.** Each end that comes from a board connector arrives
   prefilled:
   - pin count;
   - **pin labels from net names**;
   - a "mates with Main PCBA J6" name;
   - the board MPN, so the mating housing and terminal can be looked up. Matching board MPNs to a
     Loom family will often miss, so there's always a manual pick.
5. **The strongest feature: suggested wires.** If the same net name is on two ends (for example
   `I2C_SDA` on the main board's J6 and the display board's J1), Loom offers that wire. Wiring a
   board-to-board harness becomes reviewing a suggested list.
6. **Storage.** Harnesses are saved in `signoff_pl_data` (`harnesses/<id>.json`), next to PL's
   other records. PL is for FTEs only, so this fits. Loom writes a small summary back for PL: wire
   count, length, and BOM lines.

### Pitfalls

- **Mounting, shield, and peg pads** inflate pin counts. Drop pads with non-numeric names (`MH`,
  `S1`, `SH`), and show the rest for confirmation.
- **Unnamed nets** such as `Net-(J6-Pad3)` or `N$12` aren't signal names. Leave those labels blank.
- The board side and the harness side are **mirror images**, and the **genders flip**. Face views
  must say which side they show (they already do).
- Two boards can use **different net names** for the same signal, so suggestions are only
  suggestions.
- Off-board ends (sensors, wall terminals, flying leads) are purchased Parts in PL, with no
  netlist. They stay manual.

## 4. Harness software audit: options list

Sources: product docs and news found 2026-11-06, plus general knowledge. Nothing here is a
commitment. A client's in-house harness tool is also in the list, unnamed; this doc records ideas only from it, never its code or
data.

| Tool | Notable | Idea for Loom |
| --- | --- | --- |
| **WireViz** (open source, YAML → Graphviz; the PyPI listing now points to a successor, *filare*) | Text input that works in version control; connectors, cables, and bundles; IEC 60757 colors; ferrules; automatic BOM; wire numbers on cables, not bundles; documents one harness, not a system | The look (image 1). Import and export WireViz YAML. Cable vs bundle. Wire numbers shown per cable. |
| **Wirely** (image 3) | Zone-gridded sheet; one wire per line, `J6:1:-Sig1:18AWG  1:WH  Length  P2:3`; every pin row shown, used or not; build notes in the title block | Zone grid. Show empty pins. A dense one-line wire format for the table. |
| **RapidHarness** (image 2) | System block diagrams with harness counts; numbered note balloons; revision table; approvals block (drawn, engineering, manufacturing, QA) | A system view in PL. Note balloons. Approvals fed from Signoff. |
| **Splice CAD** (browser) | Drag-and-drop, browser-based harness design and documentation | The closest comparison for a web tool. Worth a hands-on look. |
| **harness.design** (browser, EV builders; beta October 2025, release April 2026), **HarnessHive**, **RecuLoom** | A newer wave of browser harness CAD | Check how each adds connectors and wires. |
| **Altium Designer harness** | Three documents: wiring diagram, layout drawing, and manufacturing drawing (Draftsman views that update from the other two); BOM from the layout; logical, electrical, and drafting checks | The same split: Connection, Layout, and Drawing. Ties into EE because Altium projects carry the boards. |
| **Zuken E3.series / E3 Harness Builder** (2025 release adds variant capture) | Connector, terminal, and seal database with wire-range rules; variants (150% harness); formboard; production documents | Variants or options. A terminal-to-gauge compatibility check (Loom has a rough one per family). |
| **Siemens Capital** | Rule checks, harness costing, manufacturing process planning, bundle diameter | A bundle diameter calculator for sleeve sizing. A cost rollup. |
| **EPLAN Harness proD** | Route in 3D from MCAD, then flatten to a 1:1 nailboard | Later: route along a PL 3D assembly. Print a 1:1 formboard on tiled pages. |
| **SOLIDWORKS Electrical / Routing** | Route in 3D, flatten to a 2D drawing, from-to lists | Import from-to lists (CSV). |
| **Arcadia (Cadonix)** | Browser-based electrical schematic tied to harness documentation | — |
| A client's in-house tool | Twists, shields, merged legs | Already in Loom's model (ideas only). |

### Feature options (pick when needed)

- [ ] WireViz YAML import and export
- [ ] From-to CSV import and export, and a continuity test table for Cirris-style testers
- [ ] Cut list or wire processing sheet: sorted by gauge and color, with cut length, strip length
      and terminal per end
- [ ] Crimp spec per terminal: wire range, tool, and pull force
- [ ] Bundle diameter, to size sleeve and heat shrink
- [ ] 1:1 formboard print, tiled across pages
- [ ] Wire and connector marker labels (printable)
- [ ] Variants (150% harness, options per build)
- [ ] Cost rollup from BOM prices
- [ ] Connector library from manufacturers' STEP (paused work: `step.js`)
- [ ] Note balloons pinned to items on the sheet
- [ ] Zone grid and an approvals block fed from Signoff sign-offs
- [ ] Netlist-driven ends and suggested wires (section 3)
- [ ] System view in PL (image 2 style)
- [ ] Layout or formboard view with editable branches, breakouts, and coverings (in the model now)
- [ ] 3D routing along a PL assembly

## Decisions

1. Name: **Loom** (2026-11-06; "Lacing" was tried and reverted the same day).
2. Cable boxes: **(b)**, built in `assets/conn.js`.
3. Connection view and EE styles: **built** 2026-11-06. The formboard editor was removed rather
   than kept as a Layout view, because the first concept could be ripped out.
4. Integration order: the **Loom prefill came first** (2026-11-06). It reads a board's
   released package from EE directly, or the latest stored run when no revision is tagged
   (`assets/boards.js`). Next: Fabcheck connectors → EE summary → PL subsection.
5. System view (2026-11-11, proposed, not decided): **in Loom, not PL**, as a second document kind that
   places boards and plugs harnesses into their connectors. See `docs/system.md`, which replaces the
   "System view in PL" option and the *Connectors & harnesses* subsection idea in section 3.
